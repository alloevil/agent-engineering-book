# 第 1 章：Agent 是什么

## 本章目标

读完本章，你应该能够：
- 精确定义 Agent，并与 Chatbot、Workflow、脚本区分开
- 理解 Agent 的五要素闭环模型
- 判断一个系统是否是 Agent，以及处于自动化光谱的哪个级别
- 评估一个任务是否适合用 Agent 解决

## 1.1 定义的必要性

"Agent"这个词在 2025-2026 年被严重滥用。几乎所有带 LLM 的产品都自称 Agent：聊天机器人叫 Agent，自动化脚本叫 Agent，甚至一个 API 包装也叫 Agent。

这种混淆不只是语义问题——它导致工程师在不需要 Agent 的场景用了 Agent（增加复杂度和不确定性），在需要 Agent 的场景用了脚本（缺乏灵活性和适应性）。

本章的第一件事，就是把 Agent 定义清楚。

## 1.2 Agent 的形式定义

我们采用 Russell & Norvig（*Artificial Intelligence: A Modern Approach*, 4th Ed）的经典定义，并针对 LLM 时代做扩展：

> **Agent 是一个通过传感器（Sensors）感知环境、通过执行器（Actuators）作用于环境、并通过内部推理选择行动以最大化目标效用的系统。**

映射到 LLM Agent：

| 经典概念 | LLM Agent 对应 |
|----------|---------------|
| 传感器（Sensors） | 上下文输入：用户消息、工具返回值、系统状态 |
| 执行器（Actuators） | 工具调用：API 请求、代码执行、文件操作 |
| 内部推理 | LLM 推理：基于上下文生成下一步行动 |
| 目标效用 | 任务目标：用户指令或系统预设目标 |
| 环境 | 运行环境：文件系统、网络、数据库、浏览器 |

更精确地，一个 LLM Agent 可以形式化为一个元组：

```
Agent = (G, P, R, A, F)
```

- **G（Goal）**：目标函数，定义"成功"是什么
- **P（Perception）**：感知函数，环境状态 → 上下文表示
- **R（Reasoning）**：推理函数，上下文 → 行动决策（由 LLM 实现）
- **A（Action）**：行动函数，决策 → 环境操作（由工具实现）
- **F（Feedback）**：反馈函数，行动结果 → 更新上下文

这五个要素形成一个闭环：

```
        ┌──────────────────────────────────────┐
        │                                      │
        ▼                                      │
   ┌─────────┐    ┌─────────┐    ┌─────────┐  │
   │    G    │───▶│    P    │───▶│    R    │  │
   │  目标   │    │  感知   │    │  推理   │  │
   └─────────┘    └─────────┘    └────┬────┘  │
                                      │       │
                                      ▼       │
                                 ┌─────────┐  │
                                 │    A    │  │
                                 │  行动   │  │
                                 └────┬────┘  │
                                      │       │
                                      ▼       │
                                 ┌─────────┐  │
                                 │    F    │──┘
                                 │  反馈   │
                                 └─────────┘
```

**缺少任何一个要素，就不是 Agent：**

| 缺少的要素 | 系统变成了 | 例子 |
|-----------|-----------|------|
| G（目标） | 聊天机器人 | ChatGPT 对话模式 |
| P（感知） | 盲推理系统 | 没有工具的纯 LLM |
| R（推理） | 自动化脚本 | Cron 定时执行 |
| A（行动） | 智能顾问 | 只给建议不执行的系统 |
| F（反馈） | 单次函数调用 | 一次 API 请求 |

## 1.3 Agent 的关键属性

基于上述定义，Agent 具备以下关键属性：

### 1.3.1 自主性（Autonomy）

Agent 在约束范围内自主决策，不需要人类指定每一步操作。

- **低自主性**：每步都需要人类确认（Human-in-the-Loop）
- **中自主性**：关键操作需要确认，常规操作自动执行
- **高自主性**：完全自主执行，仅在异常时报告人类

自主性不是越高越好。选择什么级别取决于任务的**错误成本**和**可预测性**。

### 1.3.2 反应性（Reactivity）

Agent 能感知环境变化并及时响应。工具调用失败了、目标改变了、新信息出现了——Agent 都能调整行动。

这与脚本的核心区别：脚本遇到预设之外的情况会报错或跳过，Agent 能推理出替代方案。

### 1.3.3 主动性（Pro-activeness）

Agent 不只是被动响应，还能主动采取行动实现目标。定时任务触发、异常检测、机会识别——这些都是主动性的体现。

一个 7×24 运行的 Agent 会在每天 9 点主动推送新闻，不需要人类每天提醒。

### 1.3.4 社交能力（Social Ability）

Agent 能与其他 Agent 或人类交互协作。多 Agent 系统中的消息传递、任务委托、结果汇总都属于社交能力。

## 1.4 与非 Agent 系统的精确区分

### 1.4.1 Agent vs Chatbot

| 维度 | Chatbot | Agent |
|------|---------|-------|
| 核心功能 | 生成回复 | 达成目标 |
| 状态模型 | 无状态或弱状态 | 有持续状态 |
| 行为空间 | 仅文本输出 | 工具调用 + 代码执行 |
| 时间尺度 | 单轮对话 | 多步、跨会话 |
| 自主性 | 无 | 有（在约束范围内） |
| 判断标准 | 停止输入后停止工作 | 停止输入后可继续工作 |

一个判断方法：**如果用户离开 10 分钟，系统还能继续工作吗？** Chatbot 不能，Agent 可以。

### 1.4.2 Agent vs Workflow

| 维度 | Workflow | Agent |
|------|----------|-------|
| 执行路径 | 预定义，确定性 | 动态决策，非确定性 |
| 分支逻辑 | 显式 if-else | LLM 推理 |
| 新情况处理 | 无法处理 | 能推理出替代方案 |
| 可预测性 | 高 | 低 |
| 适用场景 | 步骤固定、输入输出明确 | 需要判断和适应 |

Workflow 是"你告诉机器每一步做什么"，Agent 是"你告诉机器目标是什么"。

关键区分：**如果任务的所有可能分支都能被预先枚举，用 Workflow；否则用 Agent。**

### 1.4.3 Agent vs 脚本

| 维度 | 脚本 | Agent |
|------|------|-------|
| 推理能力 | 无（if-else 硬编码） | 有（LLM 推理） |
| 错误处理 | 预设的错误分支 | 动态推理替代方案 |
| 适应性 | 无 | 能处理未预见的输入 |
| 复杂度上限 | 低 | 高 |

脚本是 Agent 的特例——一个推理函数为硬编码 if-else 的 Agent。

## 1.5 自动化五级光谱

从脚本到自主 Agent，存在一个连续的光谱。参考 SAE 自动驾驶分级（L0-L5），我们定义 Agent 的自动化分级：

| 级别 | 名称 | 推理方式 | 人类角色 | 例子 |
|------|------|---------|---------|------|
| L0 | 手动 | 人类完成所有工作 | 执行者 | 手动操作 |
| L1 | 脚本 | 硬编码 if-else | 编写者 | Shell 脚本、cron |
| L2 | Workflow | 条件分支 + LLM 解析 | 流程设计者 | Zapier、n8n |
| L3 | Copilot | LLM 辅助，人类主导 | 决策者 | GitHub Copilot |
| L4 | Agent | LLM 主导，人类监督 | 监督者 | Claude Code |
| L5 | Autonomous Agent | 完全自主 | 目标设定者 | 研究前沿 |

**关键认知：级别越高不等于越好。**

选择什么级别取决于两个维度：
1. **任务可预测性**：步骤是否可以预先定义？
2. **错误成本**：Agent 出错的后果有多严重？

```
错误成本低 + 可预测性低 → L4（Agent）
错误成本低 + 可预测性高 → L1-L2（脚本/Workflow）
错误成本高 + 可预测性低 → L4 + 严格 Human-in-the-Loop
错误成本高 + 可预测性高 → L1-L2（脚本更可靠）
```

大多数生产环境处于 L2-L4。L5 尚未成熟，Self-Evolving Agent 仍处于研究阶段。

## 1.6 什么时候该用 Agent

决策矩阵：

| 场景特征 | 推荐方案 | 原因 |
|----------|---------|------|
| 步骤固定，输入输出格式明确 | L1 脚本 | 简单可靠 |
| 流程固定，但需要解析自然语言 | L2 Workflow + LLM | LLM 做解析，Workflow 做执行 |
| 需要理解 + 判断 + 适应未知情况 | L4 Agent | Agent 的核心价值 |
| 需要跨多个系统协调 | L4 Agent | Agent 的工具调用能力 |
| 任务高度重复，无需判断 | L1 脚本 | 脚本更高效 |
| 错误成本极高，如金融交易 | L2 + 严格审批 | Agent 的不确定性不可接受 |
| 需要从经验中学习改进 | L4 Agent + 记忆 | Agent 的反馈闭环 |

**一个常见误区：把所有自动化都升级为 Agent。**

如果你的任务可以用 cron + 脚本可靠地完成，引入 Agent 只会增加不确定性、成本和调试难度。Agent 的价值在于处理**脚本无法处理的模糊性**——当输入不确定、分支不可枚举、需要判断时。

## 1.7 案例：从脚本到 Agent 的演进

以"每天推送科技新闻"为例，看不同级别的实现：

**L1 脚本：**
```python
# cron + 固定 RSS 源
for url in RSS_FEEDS:
    articles = fetch(url)
    for article in articles:
        if keyword in article.title:
            send(article)
```
问题：关键词匹配噪音大，无法判断新闻质量。

**L2 Workflow：**
```
RSS抓取 → LLM去重 → LLM评分 → 格式化 → 推送
```
改进：LLM 做解析和评分，但流程固定。

**L4 Agent：**
```
目标：每天推送 10 条高质量科技新闻
Agent 自主决定：抓取哪些源、如何筛选、如何排序、如何格式化
失败时自动调整策略
```
改进：完全自主，能适应源变化和质量波动。

但如果你的 RSS 源很稳定，筛选规则也很明确，L2 就够了。用 L4 是过度工程。

## 本章小结

1. **Agent 的形式定义**：`(G, P, R, A, F)` 五要素闭环——目标、感知、推理、行动、反馈
2. **Agent 的关键属性**：自主性、反应性、主动性、社交能力
3. **精确区分**：Agent ≠ Chatbot（被动 vs 主动），Agent ≠ Workflow（预定义 vs 动态），Agent ≠ 脚本（硬编码 vs 推理）
4. **自动化五级光谱**：从 L0 手动到 L5 自主 Agent，选什么级别取决于任务可预测性和错误成本
5. **Agent 的适用场景**：当任务的输入不确定、分支不可枚举、需要判断时
