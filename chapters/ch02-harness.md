# 第 2 章：Harness——Agent 的缰绳

## 2.1 什么是 Harness

Harness 这个词来自马具——套在马身上的缰绳、马鞍、缰绳的总称。它不提供动力（马自己跑），但它控制马往哪跑、多快跑、什么时候停。

Agent 的 Harness 是同一个道理：

> **Harness 是 Agent 与环境之间的编排层。它不提供智能（LLM 做），但它控制 Agent 能看到什么、能做什么、怎么做、什么时候停。**

```
┌─────────────────────────────────────┐
│            Harness                  │
│  ┌─────────┐  ┌─────────┐         │
│  │ 感知控制 │  │ 行动控制 │         │
│  │ 看什么   │  │ 做什么   │         │
│  └─────────┘  └─────────┘         │
│  ┌─────────┐  ┌─────────┐         │
│  │ 流程控制 │  │ 终止控制 │         │
│  │ 怎么做   │  │ 何时停   │         │
│  └─────────┘  └─────────┘         │
└──────────────┬──────────────────────┘
               │
         ┌─────▼─────┐
         │    LLM    │  ← 推理引擎
         └─────┬─────┘
               │
         ┌─────▼─────┐
         │   Tools   │  ← 行动能力
         └───────────┘
```

**核心论点：Agent 的能力上限取决于 LLM，但可靠性上限取决于 Harness。**

一个聪明的 LLM 配上糟糕的 Harness，会做出一堆不可预测的事。一个普通 LLM 配上精心设计的 Harness，能稳定地完成任务。

## 2.2 Harness 的四维控制

### 维度一：感知控制（Perception Control）

**Agent 能看到什么？**

LLM 的推理完全取决于它看到了什么上下文。Harness 通过控制上下文来控制 Agent 的判断。

| 控制项 | 作用 | 示例 |
|--------|------|------|
| 系统提示 | 定义 Agent 的角色和约束 | "你是一个代码审查助手，只关注安全问题" |
| 工具输出 | 决定 Agent 能看到哪些工具结果 | 只返回摘要，不返回完整日志 |
| 历史记录 | 控制 Agent 能回忆多少过去 | 只保留最近 10 轮对话 |
| 外部信息 | 决定注入什么额外上下文 | 注入用户偏好、项目文档 |

感知控制的核心挑战：**信息过载和信息不足都是问题。**

- 上下文太长 → LLM 注意力分散，关键信息被淹没
- 上下文太短 → LLM 缺乏必要信息，推理质量下降

这就是为什么 Context Engineering（第 7 章）如此重要——它本质上是感知控制的工程化。

### 维度二：行动控制（Action Control）

**Agent 能做什么？**

Agent 的行动能力来自工具。Harness 通过控制工具权限来约束 Agent 的行为空间。

| 控制项 | 作用 | 示例 |
|--------|------|------|
| 工具白名单 | 只允许特定工具 | 只允许读文件，不允许写 |
| 参数约束 | 限制工具参数范围 | 只允许访问特定目录 |
| 沙箱隔离 | 限制行动的影响范围 | 在 Docker 容器内执行代码 |
| 审批机制 | 高风险行动需要人类确认 | 删除文件前需要确认 |

行动控制的核心原则：**最小权限原则。** Agent 只应该拥有完成当前任务所需的最小权限。

一个反面教材：给 Agent 完整的 root 权限，让它"自由发挥"。它可能删错文件、覆盖配置、甚至修改系统。Harness 的存在就是防止这种情况。

### 维度三：流程控制（Flow Control）

**Agent 怎么做？**

流程控制决定了 Agent 的推理-行动循环如何运转。这就是第 3 章要讲的核心模式（ReAct、Plan-and-Execute 等）在 Harness 层面的实现。

| 控制项 | 作用 | 示例 |
|--------|------|------|
| 循环模式 | 推理和行动如何交替 | ReAct 循环、Plan-Execute |
| 最大步数 | 防止无限循环 | 最多执行 20 步 |
| 重试策略 | 行动失败后怎么办 | 最多重试 3 次，指数退避 |
| 回退机制 | 整体失败时怎么办 | 回退到人类接管 |

流程控制的核心挑战：**在自主性和可控性之间取得平衡。**

- 控制太严 → Agent 灵活性被阉割，和脚本没区别
- 控制太松 → Agent 行为不可预测，可能偏离目标

### 维度四：终止控制（Termination Control）

**Agent 什么时候停？**

这是最容易被忽视、但最关键的维度。一个不知道何时停止的 Agent 是危险的。

| 终止条件 | 作用 | 示例 |
|----------|------|------|
| 目标达成 | 自然终止 | 任务完成，返回结果 |
| 最大轮次 | 防止死循环 | 超过 50 轮自动停止 |
| 超时 | 防止挂起 | 超过 5 分钟自动停止 |
| 成本上限 | 防止烧钱 | Token 消耗超过 $1 停止 |
| 人类介入 | 人工终止 | 用户发送"停止"命令 |
| 异常检测 | 安全终止 | 检测到异常行为自动停止 |

**终止控制是 Harness 的安全网。** 当其他所有控制都失效时，终止控制确保 Agent 不会失控。

## 2.3 Harness 与框架的关系

一个常见的混淆：Harness 和框架（Framework）是什么关系？

**框架是 Harness 的实现工具，Harness 是你的设计决策。**

- LangGraph 是一个框架，它提供了构建 Harness 的积木（状态、节点、边）
- 但你用 LangGraph 构建什么样的 Harness，是你的设计决策
- 同样用 LangGraph，两个人可能构建出完全不同的 Harness

```
框架（工具）        Harness（设计）        Agent（产品）
  LangGraph    →    你的控制逻辑    →    你的代码审查 Agent
  LangGraph    →    另一种控制逻辑  →    你的客服 Agent
```

这就是为什么本书不只讲框架——框架会过时，但 Harness 的设计原则不会。

## 2.4 Harness 模式

### 模式一：单循环 Harness

```
输入 → LLM 推理 → 工具调用 → 输出
```

最简单的 Harness。Agent 推理一次，行动一次，返回结果。

- 适用：简单问答、格式转换、单步工具调用
- 优势：确定性高，成本低
- 局限：无法处理多步任务

### 模式二：多步 Harness（ReAct 循环）

```
输入 → [推理 → 行动 → 观察] × N → 输出
```

Agent 反复推理和行动，直到目标达成或达到终止条件。

- 适用：需要多步操作的复杂任务
- 优势：灵活性高，能处理未知情况
- 局限：可能推理漂移、陷入循环

### 模式三：层级 Harness

```
主 Agent（规划）
  ├── 子 Agent A（执行子任务1）
  ├── 子 Agent B（执行子任务2）
  └── 子 Agent C（执行子任务3）
```

主 Agent 负责规划和协调，子 Agent 负责执行具体任务。

- 适用：大型复杂任务，需要并行处理
- 优势：分工明确，可扩展
- 局限：协调开销大，错误传播

### 模式四：协作 Harness

```
Agent A ←→ 共享状态 ←→ Agent B
              ↑
           Agent C
```

多个 Agent 共享状态，各自负责不同方面，协作完成任务。

- 适用：需要多角度分析的任务（如辩论、代码审查）
- 优势：多视角，减少盲点
- 局限：一致性难保证，协调复杂

## 2.5 Harness 的关键设计问题

### 如何处理工具调用失败？

工具调用失败是常态，不是异常。网络超时、权限不足、参数错误——Harness 必须有明确的失败处理策略。

```
策略一：重试（适合临时故障）
策略二：换工具（适合工具不可用）
策略三：跳过（适合非关键工具）
策略四：报错终止（适合关键工具）
策略五：报告人类（适合需要判断的情况）
```

### 如何防止 Agent 陷入死循环？

Agent 可能陷入"推理→行动→失败→推理→行动→失败"的死循环。

防御措施：
1. **最大步数限制**：硬性终止条件
2. **重复检测**：如果连续 3 次相同行动，强制跳出
3. **退化策略**：循环超过阈值后，切换到更简单的策略或报告人类

### 如何在自主性和可控性之间取得平衡？

这是 Harness 设计的核心张力。

- **高自主性**：Agent 自由决策，灵活但不可预测
- **高可控性**：严格约束，可靠但僵化

最佳实践：**渐进式信任。**

1. 初始状态：高可控，每步都需确认
2. 积累信任：Agent 表现稳定后，逐步放宽限制
3. 成熟状态：大部分操作自主，关键操作仍需确认

### 如何让 Agent 知道自己不知道什么？

这叫**元认知**（Metacognition）——Agent 能判断自己的推理是否可靠。

Harness 可以通过以下方式支持元认知：
1. **置信度评估**：让 Agent 对自己的推理打分
2. **外部验证**：用另一个 LLM 或规则引擎验证 Agent 的推理
3. **人类标注**：收集人类反馈，训练 Agent 的自我评估能力

## 2.6 从 Harness 角度看主流框架

每个框架都有自己的 Harness 哲学。理解这一点比学 API 更重要。

| 框架 | Harness 哲学 | 核心控制方式 |
|------|-------------|-------------|
| LangGraph | 图状态机，你定义每个节点和边 | 最灵活，完全可定制 |
| Pi | 最小 Harness，四个原语 | 极简，靠插件扩展 |
| oh-my-pi | 全能 Harness，一切内建 | LSP + DAP + 子代理 |
| Claude Code | 沙箱 + 审批 | 安全优先，人类监督 |
| Codex CLI | 沙箱 + approval 模式 | 安全优先，类似 Claude Code |
| OpenClaw | 持久化 Harness | 记忆 + 定时 + 多通道 |

**没有"最好的"Harness，只有"最适合场景"的 Harness。**

选择框架时，问自己：
1. 我需要多大的控制灵活性？
2. 我的安全要求有多高？
3. 我的任务是单次还是长期运行？
4. 我需要多少人类介入？

## 本章小结

- Harness 是 Agent 与环境之间的编排层，控制感知、行动、流程、终止
- Agent 的可靠性上限取决于 Harness，不是 LLM
- Harness 和框架是两回事：框架是工具，Harness 是设计决策
- 四种 Harness 模式：单循环、多步、层级、协作
- 核心张力：自主性 vs 可控性，通过渐进式信任来平衡
